## 0. TÓM TẮT CHO AI CODING — ĐỌC TRƯỚC KHI LÀM

### 0.1. Nhiệm vụ P0

**P0 KHÔNG phải giai đoạn xây sản phẩm CRM-CSKH hoàn chỉnh.** Nhiệm vụ là chứng minh chúng ta có thể tận dụng Frappe CRM **đúng phiên bản**, **phát triển cục bộ**, **mở rộng sạch**, **bảo vệ kho khách hàng** và **nâng cấp về sau**. Chỉ khi P0 qua cổng nghiệm thu mới bắt đầu triển khai phân phối theo tỷ lệ ở P1.

Nguyên tắc bất biến:

1. Chỉ một **web CRM** cho BOD, Admin, Team Leader và nhân viên; hiển thị tính năng theo vai trò.
2. Frappe Framework + Frappe CRM là lõi; app `crm_cskh` bổ sung nghiệp vụ. Không dựng một backend hoặc database CRM thứ hai.
3. Dữ liệu chính ở **MariaDB**; Redis phục vụ cache/hàng đợi. Không đưa Supabase/Neon vào lõi CRM.
4. Phát triển/test cục bộ; **không cần deploy VPS sau mỗi lần chỉnh code**. Không thử nghiệm trên VPS production và không dùng dữ liệu khách hàng thật trong P0.
5. **Việt hóa** tận dụng `crm/locale/vi.po` và i18n Frappe; không xây cơ chế dịch riêng.
6. Nhân viên được giao khách, sau này tự ghi kết quả liên hệ qua điện thoại, SMS, Zalo, Facebook hoặc kênh khác. P0 chỉ kiểm chứng tính khả thi, chưa xây workflow P2.
7. Kiểm soát truy cập phải nằm ở **backend/API**, không dựa vào ẩn menu trên frontend.
8. Ưu tiên `REUSE` → `CONFIGURE` → `EXTEND` → `BUILD NEW`; không sửa source `frappe` hoặc `crm` khi chưa có PoC chứng minh extension không đủ.
9. Chỉ thiết kế API dễ dùng lại cho ứng dụng điện thoại trong tương lai; không xây client điện thoại ở P0.
10. Không tự ý đổi master plan. Nếu phát hiện mâu thuẫn hoặc blocker, lập ADR và cập nhật đề xuất trước khi code lan rộng.

### 0.2. Cổng nghiệm thu quan trọng nhất

**P0 không đạt nếu nhân viên có thể đọc/ghi dữ liệu khách ngoài phạm vi qua bất kỳ đường API nào đang dùng hoặc được phép dùng.** Đặc biệt phải kiểm thử CRM Lead, Call Log, Task, Note, file đính kèm, danh sách, xuất dữ liệu và chuyển giao người phụ trách. Một giao diện có vẻ phân quyền đúng là chưa đủ.

### 0.3. Không làm ở P0

- Không viết engine phân phối theo tỷ lệ, import kho số lượng lớn, chống trùng production-ready: **P1**.
- Không làm form kết quả CSKH toàn diện, Contact Attempt, callback workflow: **P2**.
- Không làm KPI Engine, bảng điểm chất lượng, dashboard CSKH chính thức: **P3**.
- Không làm production rollout cho người dùng thật, benchmark đầy tải, hardening toàn diện: **P4**.
- Không tạo kiến trúc nhiều service mới chỉ để thay thế tính năng có sẵn của Frappe.

### 1.2. Giả định để bắt đầu mà không phải chờ hỏi lại

- Máy phát triển có thể chạy Docker/Dev Containers. Nếu dùng Windows, ưu tiên **WSL2 + Docker** và lưu source trong filesystem Linux thay vì bind mount trên ổ NTFS khi bị chậm I/O.
- DEV và môi trường kiểm thử dùng **dữ liệu giả**, không dùng backup của production hoặc số điện thoại thật.
- Sử dụng một Frappe site DEV ban đầu; có thể tạo test site riêng để chạy bộ test phá dữ liệu.
- Baseline chức năng là Frappe CRM `v1.87.0`. **Framework version và SHA phải được xác thực tương thích rồi khóa lại**; README nêu họ stable v1.x tương thích các họ Frappe v15/v16, không suy luận mọi commit của hai họ đều tương thích.

### 1.3. Định nghĩa GO / NO-GO

**GO P1** nếu tất cả điều kiện `G0-01` → `G0-10` ở §12 đạt và không còn blocker `Critical/High` ảnh hưởng quyền dữ liệu. **NO-GO** nếu bất cứ ca đọc chéo lead/customer data nào còn khai thác được, nếu app `crm_cskh` không thể triển khai/migrate ổn định, hoặc nếu UI extension không có giải pháp duy trì hợp lý.

## 2. KHÓA BASELINE MÃ NGUỒN — KHÔNG CÀI `develop` MẶC ĐỊNH

### 2.1. Repository và phiên bản cần khảo sát

| Thành phần | Nguồn | Cách khóa |
|---|---|---|
| Frappe CRM | https://github.com/frappe/crm | Tag khảo sát `v1.87.0`; xác nhận commit SHA sau checkout |
| Frappe Framework | https://github.com/frappe/frappe | Chọn nhánh stable tương thích với tag CRM, khóa commit SHA hoặc release tương thích |
| Frappe Docker | https://github.com/frappe/frappe_docker | Chọn commit/tag phù hợp để dựng DEV và tạo image; khóa revision |
| Custom app | Repo mới `crm_cskh` của dự án | Versioned riêng; thay đổi qua PR |
| Package Python/JS | Metadata/lockfiles của repo đã ghim | Không tự nâng major version ở P0 |

**Lưu ý thực tế:** `frappe/crm` có file `docker/docker-compose.yml` phục vụ phát triển/demo, chứa mật khẩu mẫu và script lấy app bằng branch trôi. **Không dùng nguyên trạng để triển khai production**. Với DEV có thể tham khảo cấu hình nhưng thay mật khẩu, pin version và chỉ mở port nội bộ.

### 2.2. Bắt buộc ghi lại provenance

Tạo `docs/architecture/version-lock.md` gồm:

```text
- CRM release tag + full commit SHA
- Frappe Framework branch/tag + full commit SHA
- frappe_docker commit SHA
- Python version / Node version / Yarn version
- Image references & digests (nếu đã build)
- MariaDB/Redis image versions & digests hoặc version constraints
- Cách tái tạo môi trường từ các revision này
- Kiểm tra license: Frappe CRM AGPL-3.0 và dependencies liên quan
```

Nếu một tổ hợp framework/CRM không hoạt động, dùng **ma trận tương thích có ghi lại kết quả**, không sửa core để cưỡng ép chạy được.

### 2.3. Lệnh kiểm chứng tối thiểu

Trong bản clone:

```bash
# Chạy trên bản checkout thích hợp; lệnh là ví dụ kiểm tra, không phải script cài đặt hoàn chỉnh.
git rev-parse HEAD
git status --short
git describe --tags --always
```

**Yêu cầu:** không ghi `latest`, `main`, `develop` làm bản phát hành cuối cùng trong lockfile. Trong quá trình clone ban đầu có thể dùng nhánh để lấy source, sau đó checkout và ghi full SHA.

## 3. P0-A — DỰNG DEV CỤC BỘ CÓ THỂ TÁI TẠO

### 3.1. Công nghệ và giải pháp được ưu tiên

- **Reuse:** [frappe_docker devcontainer](https://github.com/frappe/frappe_docker) / Frappe Bench, không tự viết lại dev orchestration.
- **App:** Frappe Framework, Frappe CRM, `crm_cskh` cùng một bench/site.
- **Database/queue:** MariaDB, Redis cache, Redis queue (theo cấu hình Dev Container được chọn).
- **Frontend:** Vue của Frappe CRM, hỗ trợ Vite dev server.
- **Tests:** runner của Frappe (`bench run-tests`) và bộ test JS có sẵn trong Frappe CRM nếu áp dụng.

### 3.2. Các bước AI Coding phải thực hiện

**A1. Khảo sát máy DEV**

- Kiểm tra Docker Compose, Git, bộ nhớ, disk, kiến trúc CPU và đường mount volume.
- Xác nhận có thể truy cập ứng dụng tại `localhost` từ máy phát triển.
- Không yêu cầu SSH/VPS production để viết hoặc debug UI/API.

**A2. Dựng Frappe Bench có service phụ trợ**

- Ưu tiên cấu hình `devcontainer-example` của `frappe_docker` hoặc cấu hình chính thức tương đương được ghim commit.
- Tạo `deploy/dev/` chứa `README.md`, compose/override, `.env.example` không có bí mật, script bootstrap lặp lại được.
- Chỉ expose cổng DEV cần thiết lên `127.0.0.1` nếu chạy trên máy cá nhân; DB/Redis không public Internet.
- Ghi rõ cách start, stop, reset, xem logs, backup/restore dữ liệu giả.

**A3. Cài Frappe CRM theo baseline**

- Khởi tạo Frappe Framework đã chọn ở §2.
- Cài app CRM bằng tag/commit SHA đã ghim.
- Tạo site `dev.localhost` (hoặc tên site dev rõ ràng).
- Kiểm tra login Administrator, trang `/crm`, Lead List, Tasks, Call Logs, Dashboard, Preferences.
- Bật `developer_mode` **chỉ trên DEV** nếu cần tạo DocType/dev migration.

**A4. Chứng minh hot reload và thay đổi backend cục bộ**

- Dùng workflow được README CRM mô tả để chạy `bench start` và frontend `yarn dev` (tại thư mục frontend đúng phiên bản).
- Thử thay một nhãn UI demo, xem kết quả trên trình duyệt rồi hoàn tác.
- Thử sửa một Python endpoint không chứa PII, reload/restart thích hợp, kiểm tra response; không dùng restart VPS.
- Chạy `bench --site dev.localhost migrate` khi có metadata/schema/patch mới; không chạy migrate chỉ vì thay nhãn UI.

**A5. Tạo seed data và tài khoản giả**

- Xem §7; tạo đầy đủ hai team, một số Lead và Call/Task mẫu.
- Có script `seed` lặp lại được; mỗi lần chạy không tạo dữ liệu trùng bất thường.

### 3.3. Lệnh minh họa — chỉ chạy khi môi trường đã sẵn sàng

```bash
# Trong Frappe Bench đã cấu hình MariaDB/Redis và install Frappe Framework.
bench --site dev.localhost list-apps
bench --site dev.localhost migrate
bench start

# Shell khác, trong frontend Frappe CRM của đúng phiên bản:
cd apps/crm/frontend
yarn install
yarn dev
```

> Những lệnh trên chỉ là phần thao tác sau khi đã dựng service và site. AI Coding phải tạo `deploy/dev/README.md` với lệnh **đầy đủ, đúng máy DEV thực tế**; không giả định mọi máy có thể chạy `bench start` ngay sau `docker compose up`.

### 3.4. Nghiệm thu P0-A

- [ ] Người thứ hai có thể setup từ repo và tài liệu, không cần hướng dẫn miệng.

### 4.3. Công việc thực thi

**B1. Scaffold từ Frappe CLI:**

```bash
# Chỉ chạy trong bench dev đã tạo.
bench new-app crm_cskh
bench --site dev.localhost install-app crm_cskh
bench --site dev.localhost list-apps
```

- Ghi tên app, mô tả, copyright và **giấy phép của phần code tự phát triển phải được xem xét cùng AGPL của core**, không tự kết luận phần nào cũng có thể đóng mã nguồn.
- Không cần thêm framework JS mới ở P0.

**B2. PoC mở rộng metadata**

- Tạo **một Custom Field thử nghiệm** trên `CRM Lead` bằng cơ chế Frappe, ví dụ `cskh_poc_marker` (`Data` hoặc `Check`), có fixture/migration quản lý.
- Chứng minh thêm/sửa/đọc field qua UI/API đúng permission.
- Chứng minh `bench migrate` trên site sạch và site đã có dữ liệu giả không làm hỏng records.
- Sau PoC: quyết định field nào giữ, **xóa marker thử nghiệm và metadata rác** trước khi kết thúc P0 hoặc ghi rõ vì sao giữ và cho mục đích gì.

**B3. PoC DocType mới**

- Tạo một DocType tối thiểu chỉ để xác minh lifecycle create → migrate → permission → read/write → cleanup; có thể dùng `CSKH App Settings` như cấu hình thực nếu đã có use case rõ.
- Nếu dùng DocType thử nghiệm, không đưa vào release sản phẩm khi không còn cần.
- Chỉ tạo `CSKH Campaign`, `CSKH Work Item`, `CSKH Assignment History` sau khi data model đã được chốt ở P1; P0 chỉ có schema draft.

**B4. PoC API tùy chỉnh**

- Tạo 1 endpoint đơn giản có xác thực (ví dụ `crm_cskh.api.health.ping`) chỉ trả trạng thái service/phiên bản an toàn, **không trả DB credentials, site config hay thông tin hệ thống nhạy cảm**.
- Kiểm thử Guest bị từ chối với API yêu cầu đăng nhập.
- Chứng minh backend kiểm permission thực tế bằng một endpoint demo đọc Lead được giao (nếu tạo endpoint này thì phải có test negative access). Hoặc tái sử dụng endpoint core để test quyền.
- Chuẩn bị quy ước JSON, lỗi validation, paging, auth, API versioning và transaction ở dạng ADR; không cần thiết kế toàn bộ API P1–P3.

**B5. Kiểm tra migration/upgrade**

- Site DEV mới → install-app → migrate → dữ liệu thử → migrate lần 2 (idempotency).
- Chạy lại test trên site sạch khác; không cho phép migration chỉ thành công nhờ trạng thái có sẵn trên máy tác giả.
- Tạo bản ghi thay đổi schema và rollback strategy. Không mặc định `bench migrate` có khả năng tự động downgrade.

### 4.4. Nghiệm thu P0-B

- [ ] `crm_cskh` hiển thị trong `list-apps` cùng Frappe CRM.

**Bắt buộc:** ghi evidence theo dạng `file:line`, link GitHub tag + SHA, kết luận `REUSE / CONFIGURE / EXTEND / BUILD NEW`, giới hạn và test chứng minh. Không sao chép file từ nhánh `develop` rồi coi đó là API của stable.

### 5.2. Rủi ro UI extension cần kiểm chứng

`v1.87.0` dùng Vue SPA có các route gắn sẵn trong `frontend/src/router.js`, base URL `/crm`. **Không được mặc định app Frappe tùy chỉnh sẽ tự chèn route/menu vào SPA gốc.** Kiểm chứng cụ thể bằng 3 phương án:

| Phương án | Cách làm | Điều kiện chấp nhận |
|---|---|---|
| **UI-A: App/page riêng, cùng Frappe site** | Dựng một page `/cskh` hoặc một route trong app mới, dùng chung đăng nhập và backend | Truy cập 1 domain, không cần auth thứ hai, điều hướng tốt, không fork core |
| **UI-B: Dùng CRM UI gốc + trường custom + liên kết tới page mới** | Tận dụng Lead/Task/List/CallLog; nút/menu dẫn sang CSKH | Ít code, không phá SPA, UX đủ thuận tiện cho nhân viên |
| **UI-C: Fork/patch frontend CRM có kiểm soát** | Thêm route/menu bằng diff nhỏ vào `crm` | Chỉ dùng nếu A/B không đáp ứng; giới hạn file sửa, CI regression, chiến lược rebase rõ |

**Quyết định mặc định trước khi có bằng chứng:** ưu tiên **B kết hợp A** (màn hình sẵn có + page nghiệp vụ cùng site), không fork core chỉ vì muốn menu đẹp hơn.

### 5.3. PoC phải thực hiện

1. Từ CRM Lead List truy cập một trang CSKH thử nghiệm cùng origin, kiểm tra session có hiệu lực.
2. Trở lại CRM không phải đăng nhập lần hai.
3. Kiểm tra quyền: user Staff chỉ thấy bản ghi được giao, không có data leakage qua API của trang CSKH.
4. Kiểm tra route `/crm/*` không bị page mới chiếm/hỏng; refresh deep link vẫn hoạt động.
5. Kiểm tra tương thích cookie/CSRF và POST request được bảo vệ.
6. Đối chiếu công sức tạo trang mới với sửa UI gốc và chi phí nâng cấp upstream.
7. Chốt ADR `ADR-UI-001`, có ảnh màn hình và demo đường dẫn.

### 5.4. Dashboard extension spike

## 6. P0-D — POC NGHIỆP VỤ CỐT LÕI: PHONE-ONLY LEAD, CALL LOG, TASK, STATUS

### 6.1. Mục tiêu

Chứng minh các module Frappe có sẵn đáp ứng được **luồng dữ liệu tối thiểu** trước khi phát triển engine CSKH mới.

### 6.2. Kịch bản D1 — tạo Lead chỉ có số điện thoại

1. Tạo số điện thoại **giả/test**, không phải số khách hàng thật.
2. Thử import/tạo bản ghi với các trường tối thiểu; ghi lại lỗi bắt buộc, đặc biệt `first_name`.
3. Áp dụng phương án tạm tên **không làm mất kiểm soát dữ liệu** (ví dụ `Khách chưa rõ tên - XXXX`, với `XXXX` là mã không nhạy cảm), đánh dấu placeholder.
4. Xác minh `mobile_no`, `status`, `lead_owner`, `source` được lưu như mong đợi.
5. Kiểm tra tạo lại Lead số tương đương với nhiều định dạng. **P0 chỉ ghi nhận khả năng trùng**, không viết dedup engine production.

**Kết quả phải rõ:** cách tạo Lead hợp lệ, các validation cần tuân thủ và đề xuất chuẩn hóa số/dedup cho P1. Không được tắt mandatory validation toàn hệ thống để import dễ hơn.

### 6.3. Kịch bản D2 — manual Call Log

1. Dùng màn hình `Call Logs → Create` hoặc tạo Call Log từ Lead theo UI chuẩn.
2. Ghi kết quả kỹ thuật `No Answer`, `Busy`, `Completed` và tham chiếu đến một Lead mẫu.
3. Kiểm tra hiển thị trong Timeline của Lead và danh sách Call Logs.
4. Xác minh một Call Log trạng thái `Completed` **không đồng nghĩa** khách “quan tâm” hoặc “chuyển đổi”.
5. Ghi phương án mapping sang `CSKH Contact Attempt` cho P2, chống đếm trùng khi có cả activity CSKH và Call Log.

### 6.4. Kịch bản D3 — Task và trạng thái

1. Tạo `CRM Task` gắn với Lead, assignee và `due_date`.
2. Đọc Task dưới vai trò owner, cấp quản lý, nhân viên khác.
3. Chuyển Lead `New` → `Contacted` → `Nurture`, kiểm tra `status_change_log`.
4. Ghi rõ Task chỉ biểu thị **việc cần làm**; chưa phải kết quả liên hệ hay điểm chất lượng.
5. Kiểm tra timezone `Asia/Ho_Chi_Minh` khi hiển thị và lưu thời hạn.

### 6.5. Kịch bản D4 — Frappe SLA

- Tạo SLA test (nếu có thể cấu hình nhanh) và kiểm tra trạng thái phản hồi.
- Ghi ranh giới: SLA gốc là SLA giao tiếp, **chưa tự giải quyết việc first-touch tính từ `assigned_at` hoặc callback deadline của dự án**.
- Không chỉnh sâu SLA core ở P0.

### 6.6. Đầu ra

## 7. P0-E — DATA SEED & MA TRẬN QUYỀN CẦN KIỂM THỬ

### 7.1. Tài khoản và cấu trúc giả

Tạo ít nhất **hai team** để kiểm tra ranh giới thực tế:

```text
Administrator        (System Manager, sử dụng kiểm tra hệ thống)
BOD_VIEWER           (vai trò xem báo cáo theo nguyên tắc least privilege; PoC role)
CRM_ADMIN            (quản lý kho/giao lead; PoC role)
TEAM1_LEADER         (Sales Manager, thuộc cây Team 1)
  ├─ STAFF_A          (Sales User)
  └─ STAFF_B          (Sales User)
TEAM2_LEADER         (Sales Manager, thuộc cây Team 2)
  └─ STAFF_C          (Sales User)
```

Các role đặc thù BOD/CRM Admin có thể bắt đầu như thử nghiệm cấu hình; **không ép BOD thành `System Manager` chỉ để xem dữ liệu**. Nếu thiếu API BOD riêng, ghi kiến trúc và tạo test stub an toàn; các quyền thực tế hoàn thiện ở P1/P3.

### 7.2. Dataset tối thiểu

- 12–20 Lead **giả lập**: Lead A1–A4 của STAFF_A, B1–B4 của STAFF_B, C1–C4 của STAFF_C, một số chưa giao.
- Một số Lead có Call Log thủ công, Note, Task, attachment giả.
- Ít nhất 1 Lead có status history.
- Một case reassignment A → B và một case chuyển team A → C.
- Mỗi bản ghi có người tạo/người giữ rõ ràng; seed deterministic, dễ reset.
- Không gọi điện/gửi SMS ra ngoài từ data seed; không sử dụng danh sách số thật.

### 7.3. Ma trận RBAC mục tiêu — P0 phải kiểm chứng đường triển khai

Ký hiệu: **A** = allowed, **D** = denied, **C** = controlled theo quyền/phạm vi; mọi quyền đều kiểm phía server.

| Thao tác | Staff owner | Staff không sở hữu | Leader cùng team | Leader khác team | BOD Viewer | CRM Admin |
|---|---:|---:|---:|---:|---:|---:|
| Xem Lead chi tiết | A | **D** | A | **D** | C | C |
| Liệt kê/tìm số của Lead | A | **D** | A | **D** | C | C |
| Chỉnh các trường CSKH được phép | C | **D** | C | **D** | D/C | C |
| Xem Call Log liên quan Lead | C | **D** | C | **D** | C | C |
| Xem Note liên quan Lead | C | **D** | C | **D** | C | C |
| Xem Task liên quan Lead | C | **D** | C | **D** | C | C |
| Tải attachment/private file | C | **D** | C | **D** | C | C |
| Export danh sách SĐT | **D** mặc định | **D** | C | **D** | C | C |
| Giao lại/thu hồi Lead | **D** | **D** | C | **D** | **D** mặc định | C |
| Xem báo cáo tổng hợp | Cá nhân | **D** ngoài phạm vi | Team | **D** team khác | Toàn công ty | C |
| Cấu hình quyền hệ thống | **D** | **D** | **D** | **D** | **D** | **D** (trừ System Manager) |

> Đây là **ma trận đích của dự án**, không phải khẳng định Frappe mặc định đã áp dụng đúng. P0 phải ghi cho từng ô: `PASS / FAIL / NOT IMPLEMENTED`, API đã dùng, bằng chứng. Những ô C cần mô tả chính xác quyền sẽ được cấp ở P1/P3.

### 7.4. API/đường truy cập buộc phải test

**Đọc danh sách:**

- `crm.api.doc.get_data` và mọi list/filter/search API mà frontend gọi.
- `frappe.client.get_list` và các API dữ liệu core tương đương nếu role gọi được.
- Truy vấn tìm số điện thoại; thử bypass filter, sửa `doctype`, thay `name` hoặc `lead_owner` tùy biến.

**Đọc chi tiết/đối tượng liên quan:**

- `frappe.client.get`, `CRM Lead` detail.
- `crm.api.activities.get_activities`, `get_lead_activities`.
- `crm.fcrm.doctype.crm_call_log.crm_call_log.get_call_log`.
- Note, Task, Comment, Attachment/File private, download URL và các metadata link.
- API `get_assigned_users` và các API nhạy cảm trả assignee/info.

**Ghi/điều chuyển:**

- Thay `lead_owner` trực tiếp, đổi `ToDo`, `DocShare` qua các route hiện có.
- `crm.api.doc.remove_assignments` và các endpoint assignment/bulk (đặc biệt cần kiểm tra tham số `ignore_permissions` do client đưa lên có thể tạo đường bypass nếu không được khóa ở backend).
- Trực tiếp sửa Call Log, Note, Task qua API; thử đối tượng thuộc lead của user khác.
- Sau khi A → B, test A không thể đọc/ghi hoặc tải tài liệu liên quan nếu không còn quyền.

**Export và đường phụ:**

- Export/CSV, bulk operations, file URLs, link lookup, global search, báo cáo, query của dropdown, web resource.
- Nếu một endpoint của role nhân viên có thể lộ danh sách/phone dù UI không hiển thị, coi là **FAIL**.

**Ghi chú quan trọng:** Không kết luận một endpoint có lỗ hổng chỉ vì đọc code thấy rủi ro. Cần chạy test thực tế với tài khoản không sở hữu. Nếu xác nhận FAIL, chặn phát hành, sửa trong custom app/permission hook hoặc phương án upstream patch tối thiểu và regression test.

## 9. P0-G — TEST FRAMEWORK, CI VÀ CHẤT LƯỢNG PR

### 9.1. Mục tiêu

Thay đổi về sau không phá phân quyền, schema hoặc tính đúng dữ liệu. **P0 phải có pipeline chạy được**, dù feature coverage còn nhỏ.

### 9.2. Đầu việc test

**Python/Frappe:**

- Dùng test framework của Frappe, tên test `test_*.py`.
- Frappe có quy tắc sử dụng **site test** (ví dụ `test_cskh.localhost`) cho destructive tests; không chạy test suite trên site production.
- Ít nhất 1 test API extension/authorization, 1 test data model/migration, các security tests mức P0 theo §7.
- Sử dụng fixtures/factory; test không phụ thuộc vào seed sinh thủ công của developer.

Ví dụ lệnh trong test environment đã thiết lập:

```bash
bench --site test_cskh.localhost run-tests --app crm_cskh
```

**Frontend:**

- Reuse test framework đang có trong `frappe/crm/frontend` (Vitest/Vite nếu dùng được tại version đã pin).

### 9.3. CI cần có

GitHub Actions trên Pull Request phải chạy tối thiểu:

1. Format/lint Python.
2. Python tests Frappe trên isolated test site, với MariaDB/Redis theo nhu cầu.
3. Frontend lint/build hoặc test tương đương cho code mới.
4. Migration/install smoke test trên một site sạch.
5. Security regression tests cơ bản ở §7.
6. Không deploy production, không đòi production secrets.

**Quy tắc:** không đánh dấu “CI PASS” nếu job bị skip hoặc runner thiếu dịch vụ, và không coi lệnh lỗi nhưng `|| true` là pass.
